# `zk-verifier`

> Verifies spending-limit proofs on-chain to authorize privacy-preserving spending.

## Overview

The `zk-verifier` contract is the on-chain proof-verification component of Stellar Payment Gateway SDK's privacy-preserving spending limits system. A prover service (running the Noir circuit in `circuits/spending_proof` and the Barretenberg toolchain) produces a spending-limit proof and signs it with the service's ed25519 key. This contract verifies that signature — and therefore that the proof was produced by the trusted prover for the given user — **without the payment amount ever appearing on-chain**.

This contract is the gateway to the `spending-rules` contract: no payment above a rule's ZK threshold is authorized unless the proof passes verification here first.

## Proof format

```
proof = [64-byte ed25519 signature][payload]
```

- `payload` commits to the spending data (e.g. a Pedersen commitment of the payment amount produced by the Noir circuit).
- The signature is produced by the trusted prover service over `user.to_string() || payload`, binding each proof to a specific user and preventing cross-user replay.

## Public API

| Function | Description |
| --- | --- |
| `initialize(admin, verifier_pk)` | Sets the admin and the prover service's ed25519 public key (32 bytes). |
| `set_verifier_pk(admin, new_pk)` | Rotates the prover key. Admin only. |
| `get_verifier_pk() -> Option<BytesN<32>>` | Returns the configured prover key. |
| `verify_spending_proof(user, proof) -> bool` | Returns `true` only for a cryptographically valid signature over `user || payload`. |

### `verify_spending_proof` semantics

1. **Fails closed** — returns `false` if no verifier key is configured or the proof is shorter than 64 bytes.
2. Recomputes the message as `user.to_string() || payload` and verifies the ed25519 signature against the configured key using the Soroban host's `ed25519_verify`.
3. **Invalid signatures panic** with a host error. Callers must invoke this contract through `try_invoke_contract` (as `spending-rules` does) and treat any invocation error as a failed verification.

## Storage Layout

| Key | Type | Purpose |
| --- | --- | --- |
| `Admin` | `Address` | Contract admin (key rotation authority). |
| `VerifierPk` | `BytesN<32>` | Prover service ed25519 public key. |

## Usage Example

```rust
use soroban_sdk::{Address, Bytes, BytesN, Env};
use zk_verifier::ZkVerifierContractClient;

// Deploy + initialize with the prover service's public key
let client = ZkVerifierContractClient::new(&env, &verifier_id);
client.initialize(&admin, &prover_pk);

// Verify a signed spending-limit proof (produced by generate_proof.sh + signer)
let is_valid = client.verify_spending_proof(&user, &proof);
```

### End-to-End Flow

```text
1. Prover service runs the Noir circuit:  nargo execute → bb prove
2. Service signs (user || commitment) with its ed25519 key
3. Proof submitted to:                   zk-verifier::verify_spending_proof()
4. Valid  → spending-rules authorizes the payment
5. Invalid → transaction rejected — amount stays private
```

## Testing

```bash
cargo test -p zk-verifier
```

Tests exercise real ed25519 cryptography (ed25519-dalek): valid proofs, tamper detection, user binding, key rotation, and fail-closed behavior.

## Design Notes

- **Real cryptographic verification** — the length-check stub was replaced with host-level ed25519 signature verification (`env.crypto().ed25519_verify`).
- **Stateful by necessity** — the verifier key must be configured (`initialize`) and is rotatable (`set_verifier_pk`), so key compromise or rotation is handled without redeployment.
- **ZK claim** — the privacy guarantee (amount never revealed on-chain) comes from the committed payload generated by the Noir circuit. Full UltraHonk on-chain proof verification remains future work pending host support for the required elliptic-curve operations; until then, the signed-commitment scheme keeps the privacy model sound and auditable.
- **Separation of concerns** — verification logic is isolated from spending authorization. `spending-rules` calls this contract and acts on the boolean result.
